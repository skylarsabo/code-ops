# CI workflows

Charter: workflow scheduling, credential boundaries, and merge-gate behavior. Excludes gate implementation details and fixture design.

`validate.yml` is the deterministic merge gate. It runs on pull requests, pushes to `main`, and manual dispatch, with per-ref cancellation. Its Ubuntu and Windows legs check package structure, generated output, dependency policy, documentation manifest, vault conformance, citation integrity, the live Atlas, and platform-sensitive regressions. Both Atlas steps pass `--gate --claims-gate`, so a STALE section or any claim that is not FRESH fails the leg. The Ubuntu leg also type-checks scripts that opt in with `// @ts-check` against the root `tsconfig.json`, using TypeScript 7.0.2 installed at an exact pin into the runner temp directory so the repository stays dependency-free.

Both deterministic legs run Node 24 from the repository `.node-version` file. Third-party actions resolve through exact commits recorded with review metadata in `.github/actions-lock.json`; the same checker covers shipped workflow examples and reachable local actions. Weekly Dependabot updates create review work for GitHub Actions but never merge it. Minor and patch updates are grouped, while majors remain individually reviewable and every accepted update must refresh the lock and regression evidence.

The first Ubuntu shard and Windows shard 3 each run `Docs gate regression eval` (`node evals/docs-gate/run.mjs`), so the docs gate and its ratchet are proven on both operating systems before merge. The validation matrix now includes run-contract, context snapshot, context bundle, worker-brief, and documentation-manifest regressions. The Linux leg also executes the complete answer-key drift loop and real calibration-store validation. The Windows leg remains a deliberate portability subset, not a duplicate of every Linux check. Its 20-minute ceiling accommodates the expanded record-regression workload and bounded hosted-runner variation without reducing coverage.

Both operating-system legs run the attack-chain graph regression. This pins path and case semantics as well as orchestration policy before merge, including distinct exploit-family fan-out, collision and resumption tracing, full-chain success proof, and independent validation.

Both validation legs run the durable record-collection regression and invoke `records check` for every collection declared by the live manifest. Their checkout requests full history and disables partial filtering. A `legacyPaths` exemption cannot exist without a collection-backed CI verifier. That configuration keeps missing checkout history distinct from genuine evidence loss and makes platform-specific path behavior visible before merge.

Model-driven deep review and OpSec review are opt-in local gates before a pull request. The local gate
binds base and HEAD SHAs, binary diff, changed paths, distinct strong-or-frontier reviewers,
and a receipt hash chain. After the branch push, publication verifies the live base and feature
refs and binds the destination repository to that Git remote. Strict required statuses prevent
later base movement from reusing the merge candidate. Weekly trend and floor calibration also
run through local Codex automation with explicit execution policy. They measure judgment
quality and do not define GitHub merge correctness.

GitHub `validate.yml` remains deterministic. It runs lint, rendering, checks, and regression
tests, including local-gate and judgment-planner fixtures, on the pull-request merge ref,
pushed `main` ref, or manual dispatch. The former deep-review, OpSec, scheduled judgment, and
floor workflows are absent. Consumer GitHub review examples remain opt-in integrations whose
credentials, events, and status policy belong to the adopter.

The Ubuntu leg's `Traceless publishing (PR commits, title, body)` step runs on pull requests only. It scans exactly the PR's commits, from `pull_request.base.sha` to `pull_request.head.sha`, not the synthetic merge commit. The title and body reach a temp file through `env`, never through script interpolation. Any hit or scanner error fails the job, which makes it the fail-closed backstop the tool-layer traceless hook relies on. The same step checks the pull request head ref, passed as `HEAD_REF` through `env`, with `node scripts/branch-name.mjs check` (`.github/workflows/validate.yml:89`), so a branch named with an AI-tool prefix or a generated token fails the job.

A separate `Direction gap link (advisory)` step follows it on pull requests (`.github/workflows/validate.yml:100`). It writes the body to a temp file through `env` and runs `scripts/check-gap-link.mjs`, which prints a note and a `::notice` annotation when the body links no row of the direction note's gap table and always exits 0. Ubuntu shard 3 and Windows shard 5 run its eval, `evals/direction-alignment/run.mjs` (`.github/workflows/validate.yml:238`, `.github/workflows/validate.yml:657`).

Ubuntu shard 2 runs agent-ledger, burndown, churn, dispatch-guard and compact-snapshot regressions; Windows shard 5 runs the ledger, burndown, churn and compact-snapshot cases, while shard 1 runs dispatch-guard. Brief-template and build-graph run on both legs (`.github/workflows/validate.yml:385`, `.github/workflows/validate.yml:721`). OpenCode lifecycle and enabled-models run on Ubuntu shard 3 and Windows shard 4 (`.github/workflows/validate.yml:259`, `.github/workflows/validate.yml:769`). Ubuntu shard 3 also runs handoff convergence, collision, peer surfaces, change feed and hook-bench smoke cases; Windows shard 5 runs peer surfaces (`.github/workflows/validate.yml:303`, `.github/workflows/validate.yml:636`). Bench smoke sets no latency gate. Both legs run context-audit and the advisory report-hook regression. The macOS host-evals job remains weekly/manual only and covers host-sensitive hooks (`.github/workflows/validate.yml:471`).

The model review gates became opt-in on 2026-09-03: `ship` asks at its first checkpoint, the local gate opens with its own checkpoint, and branch protection on `main` must require only the deterministic checks, so unreviewed changes merge on hosted CI alone while reviewed ones still carry SHA-bound statuses.

The Windows record-collection eval is path-gated as of 2026-09-03: it runs on a pull request or push only when the record scripts, their eval, the record authority, or the workflow changed (the manifest was dropped from the list the same day, because it re-syncs on nearly every change and had fired the gate on an unrelated pull request), and unconditionally on the weekly schedule and manual dispatch. Ubuntu keeps it on every change. The gate exists because that one step cost about 754 seconds of a 960-second Windows job while the Ubuntu copy cost 73. Per-step budgets now live in `.github/ci-budgets.json`, each set to the measured maximum of eight runs on Ubuntu and six runs on Windows. An advisory step runs `node scripts/ci-budget.mjs check` (`.github/workflows/validate.yml:186`), and `evals/ci-budget/run.mjs` pins its exit codes in the next step (`.github/workflows/validate.yml:189`), and the script exits 1 only under `--strict` (`scripts/ci-budget.mjs:70`). The Windows cost comes from process creation: the eval starts 866 children there, at about 0.7 s each against 0.05 s on Ubuntu.

As of 2026-09-23 each deterministic leg is sharded into parallel jobs of balanced duration, three on Ubuntu and five on Windows, with the same step multiset as the former single job. An aggregate job per leg `needs:` every shard, runs with `if: always()`, and fails unless every shard reports `success`, so a skipped or cancelled shard fails it. The Ubuntu aggregate keeps the job id `structural-lint`, which is the only status context branch protection requires, so that context still covers every Ubuntu step. `integrate-branch.mjs` selects its mirrored steps from the aggregate and the shards it needs, and lint checks the aggregate wiring. It selects the doc line-citation gate on every change, because a change to any cited file can break a citation (`ALWAYS_SELECT` in `scripts/integrate-branch.mjs`). It also prints that gate's advisories when the gate passes. The path-gated record eval is the last step of Windows shard 3, and that shard also runs the docs-gate, ladder-card, and merge-driver evals. Those steps run before the record eval, so a record-triggering run delays none of them.

The distill no-loss eval runs on the Ubuntu structural leg and on a Windows shard (`.github/workflows/validate.yml:59`, `.github/workflows/validate.yml:523`). The distill vault-mode state eval runs on both legs, in Windows shard 2 (`.github/workflows/validate.yml:62`, `.github/workflows/validate.yml:554`).

Ubuntu shard 1 runs the beat-the-bare-model bench check and its regression eval (`.github/workflows/validate.yml:91`, `.github/workflows/validate.yml:94`). The check runs no model: it validates the matrix, recomputes the vendored target digest, and proves every seed, change, and task acceptance in temporary copies. There is no Windows mirror.
